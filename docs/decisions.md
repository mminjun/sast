외부 도구 연계(SFR-009, SEC-010)의 위험이 어디에 있는지 보여주는 사례라 따로 남긴다.

- **(1) Semgrep이 룰 파일을 로케일 코덱으로 읽어 한글에서 깨진다** | Semgrep CLI가
  `read_text()`를 인코딩 지정 없이 호출해, 한국어 Windows에서는 cp949로 읽는다. 룰
  메시지가 한글이라 `UnicodeDecodeError: 'cp949' codec can't decode byte 0xec`로 룰
  로딩 자체가 실패했다. 대응은 Semgrep 호출 시 `PYTHONUTF8=1`을 환경변수로 넘기는 것.
  룰 메시지를 영어로 바꾸는 선택지도 있었지만, 진단 결과를 읽는 사람이 한국어 사용자이고
  KISA 항목명 자체가 한글이라 메시지를 유지하는 편이 맞다 | SFR-009, SEC-010
- **(2) Semgrep이 .gitignore를 존중해 작업 영역 전체를 건너뛰었다 (가장 심각)** |
  작업 영역은 `media/analysis_runs/<workspace_id>/source/`인데 `.gitignore`에 `/media/`가
  있다. Semgrep은 기본적으로 git ignore 규칙을 적용하므로 격리 디렉토리 전체가 스캔
  대상에서 빠졌다 — `scanned: 0`, 결과 0건. 그런데도 종료 코드는 0이라 실행은
  SUCCEEDED가 되고 raw_result에는 빈 results 배열이 저장된다. 즉 **파이프라인은 정상으로
  보이면서 실제로는 아무것도 분석하지 않는 상태**였다. 대응은 `--no-git-ignore` 추가.
  `.gitignore`의 `/media/` 규칙은 업로드된 고객 소스를 커밋에서 제외하는 옳은 규칙이라
  그대로 두고, 분석기 쪽에서 무시하게 한다 | SFR-008, SFR-009, SEC-007
- **(3) Semgrep이 미인증 상태에서 코드 조각을 가린다** | 결과의 `extra.lines`가 전부
  `"requires login"`으로 돌아온다. 계정을 연동하면 해결되지만, 고객 소스코드를 다루는
  도구에 외부 서비스 의존을 하나 더 만드는 선택이라 하지 않는다(`--metrics=off` 결정과
  같은 이유). 이미 우리 격리 디렉토리에 원본 파일이 있으므로 catalog/services.py의
  `_read_snippet()`이 해당 줄을 직접 읽는다. 읽는 경로는 격리 루트 안인지 다시 확인하고,
  20줄·2000자 상한을 둔다 | SFR-014, SEC-007, SEC-010
